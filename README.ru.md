# 03 · Node Realtime Engine

> WebSocket-сервер на **чистом Node.js** (`node:http` + `ws`, без Express, Nest и Socket.IO): каналы, presence, гарантированный порядок, догрузка пропущенного после переподключения, backpressure и горизонтальное масштабирование. С измерениями на десятках тысяч соединений.

## Зачем этот проект

Во флагмане и в feature flags используются фреймворки. Здесь нужно показать, что ты понимаешь **сам runtime**:

| Тема | Где проявляется |
|---|---|
| Event loop | Замеры `eventLoopUtilization` и задержек, поиск блокирующих операций, «serialize once» при fan-out |
| Backpressure | `bufferedAmount`, high/low watermark, политика медленных клиентов |
| Память | Сколько памяти стоит одно соединение, GC-паузы, утечки (heap snapshots до и после) |
| Сеть | Heartbeat, half-open соединения, лимиты файловых дескрипторов, эфемерные порты у генератора нагрузки |
| Распределённость | Порядок сообщений между узлами, resume с любого узла, drain без «грозы переподключений» |
| Протокол | Своя спецификация протокола, версионирование, subprotocol negotiation (JSON / MessagePack) |

## Что строим

Инфраструктуру реального времени, как у Pusher / Ably, только маленькую:
- **Durable-каналы**: сообщения с порядковым номером, история, resume после разрыва, at-least-once с дедупликацией на клиенте.
- **Ephemeral-каналы**: курсоры и «печатает…», без гарантий, со слиянием (последнее значение побеждает).
- **Presence**: кто в канале, несколько вкладок одного пользователя, join/leave.
- **Приватные каналы** с авторизацией.
- **Клиентский SDK** `@scope/realtime-client` (браузер + Node).
- **Демо-приложение** «Pulse Rooms»: комнаты с чатом, живыми курсорами, аватарами presence и панелью «Network lab» (отключить сеть, посмотреть, как догружаются пропущенные сообщения).
- **Собственный генератор нагрузки** на `worker_threads` со сценариями.

## Главные гарантии (каждая проверяется тестом)

1. В durable-канале все подписчики на всех узлах получают сообщения **в одном и том же порядке** (`seq` без пропусков).
2. Клиент, переподключившийся к **любому** узлу с `lastSeq`, получает все пропущенные сообщения, пока они есть в истории, или явный сигнал `reset`, если история уже обрезана.
3. Повторная отправка сообщения с тем же `clientMsgId` не создаёт дубль.
4. Медленный клиент не влияет на других: память узла ограничена, медленного клиента отключают с кодом `4008` и он делает resume.
5. Drain узла не создаёт пик переподключений: клиенты переподключаются с jitter.
