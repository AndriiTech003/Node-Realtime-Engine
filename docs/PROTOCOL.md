# PROTOCOL · Pulse Realtime Protocol v1

## Транспорт

- WebSocket, URL: `wss://host/v1/connect?ticket=<ticket>`
- Subprotocol negotiation (`Sec-WebSocket-Protocol`): `pulse.v1.json` (по умолчанию) или `pulse.v1.msgpack`. Кодек выбирается один раз на соединение.
- Максимальный размер фрейма: 64 KB (`maxPayload`). Превышение → закрытие с кодом `1009`.
- permessage-deflate **выключен** по умолчанию: CPU и память на каждое соединение дороже выгоды для маленьких сообщений. Замер в LEARNINGS.md, флаг конфигурации есть.

## Аутентификация: ticket

1. Клиент с обычным JWT делает `POST /v1/tickets` (HTTP на том же сервере).
2. Сервер выдаёт одноразовый `ticket` (случайные 32 байта, base64url) с TTL 30 сек, в Redis: `ticket:{t} → {userId, claims}`.
3. Клиент подключается с `?ticket=`. Сервер делает `GETDEL` (атомарно, одноразово).

Почему не JWT в URL: URL попадает в логи прокси и историю. Почему не заголовок: браузерный WebSocket API не даёт ставить заголовки. Ticket короткоживущий и одноразовый.

## Формат фрейма

Каждый фрейм — объект с полем `t` (type). Короткие имена полей нужны, чтобы сэкономить трафик при fan-out.

### Client → Server

| t | Поля | Описание |
|---|---|---|
| `sub` | `id, ch, from?` | Подписка. `from` = последний полученный `seq` для resume. Без `from` — только новые сообщения (+ опционально `history: n`) |
| `unsub` | `id, ch` | |
| `pub` | `id, ch, d, cmid` | Публикация в durable-канал. `cmid` = clientMsgId (UUID) для идемпотентности |
| `eph` | `ch, d` | Ephemeral (курсор, typing). Без подтверждения |
| `pres` | `id, ch, meta?` | Обновить свои presence-метаданные (например, статус) |
| `ping` | `ts` | App-level ping (браузер не может отправлять WS ping) |

`id` — номер запроса на клиенте для корреляции с ответом.

### Server → Client

| t | Поля | Описание |
|---|---|---|
| `hello` | `cid, node, hb, v` | После подключения: id соединения, узел, интервал heartbeat, версия протокола |
| `ok` | `id, ...` | Успешный ответ на `sub` (`seq` — текущий последний номер, `presence`) и на `pub` (`seq`, `mid`) |
| `err` | `id?, code, msg` | Ошибка запроса |
| `msg` | `ch, seq, mid, d, ts, from` | Сообщение durable-канала. `seq` непрерывен в рамках канала |
| `eph` | `ch, d, from` | Ephemeral-сообщение |
| `pj` / `pl` / `pu` | `ch, uid, meta?` | Presence join / leave / update (по пользователю, не по соединению) |
| `reset` | `ch, seq` | История до `from` недоступна: клиент должен перезагрузить состояние (например, через HTTP) и продолжить с `seq` |
| `lag` | `ch` | Сервер начал отбрасывать ephemeral-сообщения этому клиенту из-за backpressure |
| `drain` | `after` | Узел выключается: переподключиться через `after` мс (случайная задержка) |
| `pong` | `ts` | |

### Пример

```text
C: {"t":"sub","id":1,"ch":"room:42","from":1180}
S: {"t":"msg","ch":"room:42","seq":1181,"mid":"…","d":{"text":"hi"},"ts":1759250000123,"from":"u_7"}
S: {"t":"msg","ch":"room:42","seq":1182, …}
S: {"t":"ok","id":1,"seq":1182,"presence":[{"uid":"u_7","meta":{"name":"Ann"}}]}
C: {"t":"pub","id":2,"ch":"room:42","cmid":"9b2…","d":{"text":"hello"}}
S: {"t":"msg","ch":"room:42","seq":1183,"mid":"…","d":{"text":"hello"},"from":"u_1"}
S: {"t":"ok","id":2,"seq":1183,"mid":"…"}
```

Порядок в resume: сначала история (`seq > from`), потом `ok`, потом live. Сервер буферизует live-сообщения, пришедшие во время чтения истории, и отдаёт их после, отбрасывая дубли по `seq`. Это классическая гонка «история + live», её разбор должен быть в SPEC.

## Коды закрытия

| Код | Значение | Поведение клиента |
|---|---|---|
| 1000 | Нормальное закрытие | Не переподключаться |
| 1001 | Going away (drain) | Переподключиться с задержкой из `drain` |
| 1009 | Слишком большой фрейм | Баг клиента, логировать |
| 4001 | Невалидный или просроченный ticket | Получить новый ticket, переподключиться |
| 4003 | Доступ запрещён | Не переподключаться |
| 4008 | Медленный клиент (backpressure) | Переподключиться сразу, сделать resume |
| 4029 | Превышен rate limit | Переподключиться с backoff |
| 4400 | Нарушение протокола (невалидный фрейм) | Баг клиента |

## Коды ошибок (`err.code`)

`BAD_REQUEST`, `UNKNOWN_CHANNEL_TYPE`, `FORBIDDEN`, `NOT_SUBSCRIBED`, `RATE_LIMITED`, `PAYLOAD_TOO_LARGE`, `TOO_MANY_SUBSCRIPTIONS` (лимит 100 на соединение), `INTERNAL`.

## Каналы

| Префикс | Тип | Кто может подписаться / писать |
|---|---|---|
| `room:{id}` | durable + presence + ephemeral | Любой аутентифицированный (в демо), ACL-хук в проде |
| `user:{id}` | durable, приватный | Только сам пользователь; писать — только сервер (HTTP API) |
| `broadcast:{name}` | durable, только чтение | Все; писать — только сервер |

Server-side publish: `POST /v1/publish {ch, d}` с серверным ключом. Так бэкенд приложения (например, проект 01) отправляет уведомления.

## Гарантии (итог)

| | Durable | Ephemeral |
|---|---|---|
| Порядок | Полный, единый для всех подписчиков | Не гарантирован |
| Доставка | At-least-once в пределах окна истории (10 000 сообщений или 24 ч на канал) | At-most-once, может отбрасываться |
| Дедупликация | На клиенте по `seq`; на сервере публикации по `cmid` (окно 5 мин) | Нет |
| Слияние | Нет | Да: последнее значение на отправителя за 50 мс |

## Версионирование

- `v` в `hello`. Новые необязательные поля добавляются без смены версии, клиент игнорирует неизвестные поля и типы фреймов.
- Ломающие изменения → `pulse.v2.*` subprotocol, сервер поддерживает v1 и v2 одновременно минимум один мажорный релиз.
